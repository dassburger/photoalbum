* Photo Album Publisher

** Overview
Build a system to publish curated albums from the =~/Pictures= photo archive
as a password-protected (with optional public albums) responsive web photo
gallery, per =initial-prompt.org=. The system has exactly two moving parts:

- A Python CLI (=prep=), run by hand inside its own container, that reads
  per-album manifests from =~/Pictures=, extracts photo/video metadata,
  generates thumbnails/poster-frames and fully static HTML directly inside
  each album's own folder (plus a small site-wide output directory for the
  top-level index/static assets/public covers), and regenerates Caddy's
  routing/auth config.
- Caddy, the only continuously-running container, serving the real
  =~/Pictures= tree (plus the small site-wide output directory) over HTTPS
  (automatic Let's Encrypt renewal) with per-album HTTP Basic Auth, blocking
  work-in-progress content via a =path= matcher plus =respond ... 404= in
  each album's route.

No database, no backend service, no admin web UI. User accounts and
per-album access lists are plain YAML files hand-edited (and CLI-managed)
alongside the album manifests. Original photos/videos in =~/Pictures= are
never copied or modified — Caddy serves them directly. The only new things
written into =~/Pictures= are generated artifacts (thumbnails/poster frames
under a =.web/= subdirectory, and the generated =index.html= and =picture/*.html=
pages) placed alongside the originals; nothing existing is ever touched.
Neither Pillow, ffmpeg, nor any other =prep= dependency is ever installed on
the host — =prep= runs inside its own container image.

  writing anything for that album. A failed/interrupted run must never leave
  partial generated files mixed in with the user's real photos.

** Solution Overview
- *Stack*: Python (Pillow, piexif, ffmpeg/ffprobe via subprocess,
  Jinja2, ruamel.yaml, bcrypt, click, pytest) for the =prep= CLI, packaged as
  its own Docker image so none of it touches the host. Plain HTML/CSS/vanilla
  JS for the frontend — no build step, no JS framework. Caddy for TLS
  termination, static serving, and per-path Basic Auth.
- *Why Caddy, not reproxy or nginx*: Caddy has long-proven built-in automatic
  Let's Encrypt renewal, built-in =file_server= (with a =hide= subdirective
  and =not path= matchers precise enough to implement our exclusion rules
  without a mirror — see below), built-in per-path =basic_auth= with bcrypt,
  and a graceful reload (=docker compose exec caddy caddy reload=, see Task
  12) — matching what we need with the least moving parts. (reproxy has no
  equivalent exclusion mechanism; nginx's native ACME support is new,
  HTTP-01-only, and not default-enabled.)
- *Why no backend/database*: individual accounts + per-album ACLs are fully
  expressible as Caddy's per-path =basic_auth= matchers within a single site
  block, generated from two YAML sources. Removing the backend removes an
  entire running service and its failure modes.
- *Why serve =~/Pictures= directly, with no symlink mirror*: within each
  album's own route, a =path= matcher (e.g. =path /work/* /publish.yaml=)
  combined with =respond ... 404= blocks exactly =work/= (at any depth —
  Caddy documents a trailing =/*= as covering nested directories) and
  =publish.yaml=, before =file_server= ever runs. This is deliberately *not*
  =file_server='s =hide= subdirective: Caddy's own docs note =hide= is a
  "pretend it doesn't exist" convenience for serving/listing, not a security
  boundary, and its comparison is case-sensitive (a mismatched-case request
  on a case-insensitive filesystem could slip through) — a =path= matcher is
  case-insensitive and is a real routing decision. An earlier design built a
  parallel tree of symlinks back into =~/Pictures=
  as a per-file whitelist, to guarantee an un-curated JPEG could never be
  served even by direct URL guess. That guarantee is now relaxed in favor of
  simplicity: *every* file inside an album folder except the fixed =work/=
  subdirectory and =publish.yaml= is reachable if someone knows/guesses its
  exact URL, even if it isn't in the manifest's =items= list and so appears
  on no page and is linked from nowhere. This is accepted as a workflow
  convention (keep anything not ready to publish inside =work/=) rather than
  a technical guarantee, in exchange for a much simpler system: no mirror to
  build/maintain, no dual bind-mount, and the Caddyfile never needs
  regenerating just because an album's =items= changed (only ACL/user/album
  changes still require that, exactly as before).
- *Why generated HTML lives in the album folder root, not under =.web/=*:
  thumbnails and poster-frames (many small binary files) go under
  =<album>/.web/thumbs/= to avoid cluttering the folder when browsing it
  normally, but the two bookmarkable HTML artifacts — the album grid page and
  each picture's page — are written directly as =<album>/index.html= and
  =<album>/picture/<name>.html=. This means Caddy needs *zero* rewrite rules:
  a plain =file_server= on the real album directory already serves
  =/album/= and =/album/picture/IMG_0001.html= correctly via its own default
  index-file behavior, with the =path=-matcher-plus-=respond= block (see
  above) covering =work/= and =publish.yaml=. The alternative (everything,
  including HTML, under
  =.web/=) was considered and rejected because it would require per-album
  Caddy =rewrite= rules mapping clean URLs to =.web/= paths — real added
  complexity for a cosmetic benefit.
- *Why =prep= runs in its own container*: Pillow, piexif, ffmpeg/ffprobe,
  bcrypt, etc. never get installed on the host. =prep= is built as a Docker
  image (Task 16) and invoked ad hoc via =docker compose run --rm prep
  <args>= — it's not a long-running service, so it isn't part of =docker
  compose up=, only =docker compose run=.
- *Inline =style= attributes — the one narrow exception*: "never raw CSS in
  HTML/JS" does not forbid a =style= attribute that sets *only* CSS custom
  properties consumed by a predefined class rule (e.g.
  =style="--row: 3; --col-span: 2"= feeding =.album-tile { grid-row:
  var(--row) / span 1; }=). It forbids literal property values
  (=style="color: red"=). This is required because per-item grid placement
  and index cover-scatter offsets are computed per-instance in Python and
  have no finite class enumeration. Task 7's "no inline styles" test enforces
  this narrower rule, not a blanket ban on the =style= attribute.
- *Index privacy tradeoff (flagged for your review)*: the albums index needs
  to show every album's title and cover thumbnails to work as a single public
  landing page (including for anonymous visitors and as the logout
  redirect target), but cover thumbnails for *private* albums live inside
  that album's auth-protected folder. Resolution: =prep publish= also copies
  each album's chosen cover thumbnails into a separate, always-public
  =site/.covers/<album-path>/= directory (outside =~/Pictures= entirely, in
  the project repo's generated output). This means a private album's *title
  and 2-3 small cover thumbnails* are visible to anyone who can reach the
  index at all (not the full album content, which stays behind that album's
  password) — a deliberate, modest metadata leak consistent with the
  low-stakes "family-shared album" risk tolerance already agreed on. Revisit
  this if it's not acceptable once you see it rendered.
- *Remote "admin" access without a web admin UI*: instead of a bespoke admin
  interface, the user will occasionally run a Claude Code instance inside
  this project directory with Remote Control enabled, so adjustments (adding
  a user, editing a =publish.yaml=, re-running =prep publish=, checking
  =prep sync-routes= output) can be made conversationally from another
  device while away from this computer. This requires no new code — it's a
  documented operating pattern, covered in the README (see Task 18).
- *Why manifests inside the album folder*: keeps curation (notes, ordering,
  access list) colocated with the photos it describes, matching how the user
  already works with Darktable project files per-folder. Risk of leaking
  passwords is moot since only usernames (never hashes) appear there, and
  =publish.yaml= itself is hidden from Caddy's =file_server= so it's never
  web-reachable regardless.
- *Why fully static, server-rendered HTML* (vs. a JSON+SPA or hybrid
  approach): every album/picture needs its own bookmarkable URL; generating
  real =.html= files gives that for free, requires no client-side router, and
  keeps the "just serving static files" requirement exactly true. JS is
  strictly a progressive enhancement (swipe, keyboard nav, hover buttons) —
  core navigation works via plain =<a href>= links with no JS at all.

*** =publish.yaml= (one per album, inside =~/Pictures/<album>/=)
#+begin_example
title: "Family Reunion 2024"     # optional, defaults to folder name
public: false
allowed_users: [alice, bob]       # ignored if public: true

items:                            # optional; auto-populated by date if omitted
  - file: IMG_0001.jpg
  - file: IMG_0002.jpg
  - note: "This was the day it rained the whole afternoon..."
  - file: VID_0003.mp4
  - file: IMG_0004.jpg
#+end_example
A =work/= subdirectory inside the album folder (fixed name, not configurable)
holds CR2s, Darktable project files, and rejected JPEGs. Both =work/= and
=publish.yaml= itself are blocked by a =path= matcher plus =respond ... 404=
in the album's generated Caddy route (case-insensitive, covering nested
directories under =work/=) and so are never web-reachable, regardless of
what =items= does or doesn't reference.

*** =users.yml= (project repo root)
#+begin_example
alice: $2y$10$abc123...
bob: $2y$10$def456...
#+end_example
Only bcrypt hashes; plaintext passwords never touch disk. Edited by hand or
via =prep users add/passwd/delete=, always through =ruamel.yaml= round-trip
mode so comments/order/formatting survive script-driven edits.

*** Processing flow (=prep publish <album-folder>=)
1. Parse and validate =publish.yaml= (hard-fail on unknown user or missing
   referenced file) *before* writing anything.
2. Extract per-item metadata (EXIF date / ffprobe creation time, mtime
   fallback with a warning). GPS EXIF is left untouched.
3. Generate thumbnails and video poster-frames directly into
   =<album>/.web/thumbs/= (atomic write-then-rename), removing any
   thumbnails left over from items no longer in the manifest, and copy the
   chosen index-cover thumbnails into the always-public
   =site/.covers/<album>/=.
4. Group items by local day; compute grid positions.
5. Render the album page directly to =<album>/index.html=, one picture-view
   page per item directly to =<album>/picture/<name>.html= (removing any
   page left over from an item no longer in the manifest), write this
   album's =.web/album.json= summary, and re-render the top-level
   =site/index.html= (across *all* previously-published albums).
6. Sync shared static assets into =site/static/= (cheap, idempotent).
7. Regenerate the full Caddyfile (all known albums, not just this one) — each
   album route's =root= points directly at its real folder under the mounted
   =~/Pictures=, with a =path= matcher plus =respond ... 404= blocking
   =work/= and =publish.yaml= before =file_server= runs — validate it, and
   trigger a graceful reload via =docker compose exec=.
